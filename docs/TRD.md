# TRD - Todo 앱 (초안)

> 기준 문서: docs/PRD.md, docs/IDEA.md, 프로젝트 규칙 문서(CLAUDE.md)
> 상태: 초안. PRD의 "결정이 필요한 것"은 이 문서에서도 정하지 않고 **미결정**으로 표시합니다.
> API 경로, 응답 형식, 테이블 구조의 자세한 내용은 docs/API_SPEC.md, docs/DATA_MODEL.md에서 확정합니다. 이 문서에 나오는 예시는 이해를 돕기 위한 것입니다.

## 1. 목적
- PRD에 적힌 기능(F-01 ~ F-05)을 **어떤 기술로, 어떤 구조로** 만들지 정리한다.
- 각 기술을 왜 골랐는지 초보자도 이해할 수 있게 적는다.
- 화면에서 버튼을 누른 뒤 DB에 저장되기까지의 흐름을 단계별로 보여준다.

## 2. 기술 스택과 고른 이유

| 기술 | 역할 | 왜 골랐나 (한 줄 설명) |
|------|------|------------------------|
| Next.js 15 (App Router) | 웹 앱 뼈대 | 화면(프론트엔드)과 API(백엔드)를 한 프로젝트 안에서 같이 만들 수 있어서 따로 서버를 세울 필요가 없다. |
| React 19 | 화면 만들기 | 화면을 "컴포넌트"라는 작은 조각으로 나눠 만들고, 데이터가 바뀌면 화면이 알아서 다시 그려진다. |
| TypeScript (strict) | 프로그래밍 언어 | 변수에 "이건 문자열, 이건 숫자"처럼 타입을 붙여서, 실행하기 전에 실수를 미리 잡아 준다. |
| Tailwind CSS | 화면 꾸미기 | `p-4`, `text-red-500` 같은 짧은 이름을 붙이기만 하면 돼서 CSS 파일을 따로 관리하지 않아도 된다. |
| MySQL 8 | 데이터베이스 (v0.3부터) | 서버를 껐다 켜도 할 일이 남도록 저장하는 곳이고, 가장 널리 쓰이는 DB 중 하나라 자료와 예제가 많아 초보자가 막혔을 때 찾아보기 쉽다. |
| mysql2 | MySQL 접속 드라이버 (v0.3부터) | Node.js에서 MySQL에 접속해 SQL을 보내는 표준 라이브러리이고, ORM 없이 SQL을 직접 써서 DB가 실제로 어떻게 동작하는지 배울 수 있다. |
| Zod | 입력값 검사 | "제목은 1~100자" 같은 규칙을 한 곳에 적어 두고 화면과 서버에서 똑같이 검사할 수 있다. |
| Jest + React Testing Library | 테스트 | 코드가 명세대로 동작하는지 자동으로 확인하고, 사용자가 실제로 버튼을 누르는 것처럼 화면을 테스트할 수 있다. |

## 3. 전체 구조

```
[브라우저]                          [Next.js 서버]                     [DB]
 화면 컴포넌트  ── fetch 요청 ──▶  API 라우트 (app/api/...)
 (src/components)                    │
       ▲                             ▼
       │                         Zod 검사 → 서버 로직 (src/lib) ── mysql2 (SQL) ──▶ MySQL
       └──────── JSON 응답 ◀─────────────────────────────────────────────────┘
```

### 폴더별 역할
| 폴더 | 들어가는 것 |
|------|-------------|
| app/ | 페이지와 API 라우트 |
| src/components/ | 화면 컴포넌트 (입력창, 목록, 할 일 한 줄 등) |
| src/lib/ | 서버 로직, DB 연결, 테이블 생성 SQL |
| src/types/ | 화면과 서버가 함께 쓰는 타입 (예: Todo) |
| docs/ | 명세 문서 |

## 4. 버전별 기술 범위

| 버전 | 쓰는 기술 | 데이터 저장 위치 | 비고 |
|------|-----------|------------------|------|
| v0.1 | Next.js, React, TypeScript, Tailwind, Zod, Jest | 브라우저 메모리 (localStorage 사용 여부 **미결정**) | API, DB 없음 |
| v0.2 | + API 라우트 | 서버 메모리 (서버 안의 배열) | 서버를 끄면 사라짐 |
| v0.3 | + MySQL 8, mysql2 | DB | F-05 완전히 충족. MySQL을 둘 곳 **미결정** |
| v0.4 | v0.3과 같음 | DB | 수정, 필터 추가 |
| v1.0 | v0.3과 같음 + 배포 | DB (배포 환경) | 배포 후 접근 제한 방법 **미결정** |

- 현재 버전 범위를 넘는 기술은 미리 넣지 않는다. (예: v0.1에서 DB 패키지를 설치하지 않는다.)

## 5. 버튼을 누른 뒤 DB에 저장되기까지의 흐름 (F-01 할 일 추가, v0.3 기준)

사용자가 입력창에 "우유 사기"를 적고 **추가** 버튼을 누른 상황입니다.

| 단계 | 어디서 | 무슨 일이 일어나나 |
|------|--------|--------------------|
| 1 | 브라우저 (화면 컴포넌트) | 사용자가 입력창에 제목을 적는다. React가 입력값을 상태(state)에 담아 둔다. |
| 2 | 브라우저 (화면 컴포넌트) | 사용자가 **추가** 버튼을 누르면 버튼에 연결된 함수(이벤트 핸들러)가 실행된다. |
| 3 | 브라우저 (Zod) | 앞뒤 공백을 지운 제목이 1~100자인지 먼저 검사한다. 틀리면 서버에 보내지 않고 화면에 이유를 보여준 뒤 멈춘다. |
| 4 | 브라우저 → 서버 | `fetch`로 서버의 API 라우트에 요청을 보낸다. 제목은 JSON으로 담아 보낸다. (예: `POST /api/todos`, `{ "title": "우유 사기" }`) |
| 5 | 서버 (API 라우트, app/api/) | 요청을 받아 JSON 본문을 꺼낸다. |
| 6 | 서버 (Zod) | 같은 규칙으로 **한 번 더** 검사한다. 브라우저 검사는 우회될 수 있으므로 서버 검사가 진짜 관문이다. 틀리면 실패 응답을 돌려준다. |
| 7 | 서버 (src/lib 서버 로직) | 검사를 통과한(공백을 지운) 제목으로 "할 일 추가" 함수를 부른다. 이때 `crypto.randomUUID()`로 새 id를 만든다. |
| 8 | 서버 (mysql2) | `INSERT INTO todos (id, title) VALUES (?, ?)` SQL을 DB에 보낸다. 값은 `?` 자리에 따로 넘겨서, 제목에 이상한 문자가 들어 있어도 SQL이 깨지지 않게 한다(SQL 인젝션 방지). |
| 9 | DB (MySQL) | 새 행을 저장한다. 완료 여부(기본값: 미완료)와 만든 시각은 DB가 채운다. MySQL은 저장한 행을 바로 돌려주지 않으므로(`RETURNING` 없음), 서버가 7단계의 id로 방금 저장한 행을 한 번 더 읽어 온다. |
| 10 | 서버 → 브라우저 | API 라우트가 저장된 할 일을 JSON으로 응답한다. |
| 11 | 브라우저 (화면 컴포넌트) | 응답받은 할 일을 목록 상태의 **맨 위**에 넣는다(최신순, F-02). 입력창을 비운다. |
| 12 | 브라우저 (React) | 상태가 바뀌었으므로 React가 목록을 다시 그린다. 사용자는 새 할 일을 바로 본다. |

### 실패하면?
- **검사 실패 (3, 6단계)**: 할 일을 저장하지 않고 사용자에게 이유를 보여준다. (PRD 사용자 스토리 F-01)
- **서버나 DB 오류 (8~10단계)**: 목록에 추가하지 않고 "저장하지 못했다"는 메시지를 보여준다.
- 응답 코드와 오류 메시지 형식은 docs/API_SPEC.md에서 정한다.

### 버전마다 달라지는 부분
- **v0.1**: 4~10단계가 없다. 3단계 검사를 통과하면 바로 11단계로 가서 브라우저 상태에만 넣는다.
- **v0.2**: 8~9단계 대신 서버 메모리의 배열에 넣는다. 나머지는 같다.
- **v0.3 이후**: 위 표 그대로.

### 다른 기능도 같은 모양으로 흐른다
| 기능 | 버튼/동작 | 서버에서 하는 일 |
|------|-----------|------------------|
| F-02 목록 보기 | 페이지 열기 | DB에서 만든 시각 기준 최신순으로 읽어 온다. 완료 여부로는 정렬하지 않는다. |
| F-03 완료 전환 | 체크박스 누르기 | 화면이 바꿀 값을 직접 보낸다(예: `PATCH /api/todos/{id}`, `{ "completed": true }`). 서버는 받은 값 그대로 저장한다. |
| F-04 삭제 | 삭제 버튼 누르기 | 해당 할 일을 DB에서 지운다. (삭제 확인 창 여부 **미결정**) |

## 6. 입력값 검사 (Zod)
- 제목 규칙은 Zod 스키마 **하나**로 만들고 화면과 서버가 같은 스키마를 쓴다. 규칙이 두 군데로 갈라지지 않게 하기 위해서다.
- 앞뒤 공백을 지운 뒤 길이를 센다. 저장도 공백을 지운 제목으로 한다.
- 글자 수는 눈에 보이는 글자 하나를 1자로 센다. 브라우저와 Node.js에 들어 있는 `Intl.Segmenter`를 써서 세므로 따로 설치할 라이브러리는 없다.
  - 그냥 `.length`를 쓰면 이모지 "👍🏻"가 4자로 세어지기 때문이다.
- 경계값: 0자 실패, 1자 성공, 100자 성공, 101자 실패, 공백만 입력하면 실패. (PRD 7. 성공 기준)

### 완료 전환을 "값 보내기"로 정한 이유
- "반대로 바꿔" 방식은 같은 요청이 두 번 가면 원래대로 돌아가 버린다. 바꿀 값을 직접 보내면 두 번 보내도 결과가 같다.
- v0.4의 "수정" 기능도 같은 PATCH 요청에 `title`만 더하면 된다.

## 7. 테스트 방침
- Zod 스키마: 경계값(0, 1, 100, 101자)을 단위 테스트로 확인한다.
- 화면 컴포넌트: React Testing Library로 입력 → 버튼 클릭 → 목록에 보이는지 확인한다.
- API 라우트와 서버 로직: 추가, 목록, 완료 전환, 삭제가 명세대로 동작하는지 확인한다.
- 테스트를 삭제하거나 skip하지 않는다. 실패하면 구현 코드를 고친다.
- 자세한 테스트 목록은 docs/TEST_CASES.md에서 정한다.

## 8. 코딩 규칙 (기술 관련)
- TypeScript strict 모드를 켜고 `any` 타입을 쓰지 않는다.
- 화면과 서버가 함께 쓰는 타입은 src/types/에 둔다.
- 주석은 초보자가 이해할 수 있게 한국어로 짧게 쓴다.
- `console.log`는 디버깅 후 지운다.
- SQL에 값을 넣을 때는 문자열을 이어 붙이지 않고 항상 `?` 자리표시자를 쓴다.
- MySQL 테이블의 문자셋은 `utf8mb4`로 한다. 한글과 이모지를 깨지지 않게 저장하기 위해서다.
- DB 접속 주소 같은 비밀값은 코드에 직접 쓰지 않고 환경 변수(`.env.local`)에 두며, 이 파일은 git에 올리지 않는다.
